# タグ目視確認シート（フェーズ1）

Myu Kanri さん・椎名さんにケースのタグを目視確認・修正してもらうための
Google スプレッドシートを作る一式。編集面は Google スプレッドシート、
GitHub 側は生成スクリプトと確定データの保管に使う。作成: 2026-07-30。

## 対象

椎名さん確認の **88件**（全95件から音信不通7件を除外）。
アーカイブ38件 / 進行中50件。`shiina_list.tsv` が椎名さんのリストの写しで、
タイトル文字列で `cache/cases_list.json` の `case_id` に紐づけている。

全角スペースやダッシュの差で表記が揺れる16件があるため、照合は
NFKC正規化＋波ダッシュ・各種ダッシュ・引用符・空白の吸収を通してから行う。
1件でも照合できなければスクリプトは中止する（黙って落とさない）。

## ファイル

| ファイル | 役割 |
|---|---|
| `shiina_list.tsv` | 椎名さん作成の88件リスト（件数 / 状況 / メモ / ケース名） |
| `make_tag_review.py` | インポート用CSVを生成 |
| `setup.gs` | スプレッドシート側の書式・プルダウン・保護・補助シートを一括設定 |
| `ingest_reviewed.py` | 確認済みシートを読み戻して検証し、フェーズ2の入力を作る |
| `out/tag_review.csv` | インポートするCSV（生成物） |
| `out/id_map.tsv` | No ↔ case_id 対応表 |

## 手順

### 1. CSVを生成

```bash
python3 tag_review/make_tag_review.py
```

照合結果・上限超過ケース・タグ件数が標準出力に出る。

### 2. スプレッドシートを作る

1. 新規スプレッドシートを作成
2. **ファイル > インポート** で `out/tag_review.csv` を取り込む
   （インポート場所「現在のシートを置換する」、区切り文字「カンマ」）
3. **拡張機能 > Apps Script** を開き、`setup.gs` の中身を全部貼り付けて保存
4. 関数 `setup` を実行（初回のみ権限承認）

`setup` は冪等なので、CSVを差し替えて何度でも実行できる。

### 3. ドロップダウンの仕上げ（手作業・1回だけ）

**「複数の選択肢を許可」とチップ色は Apps Script / Sheets API v4 では設定できない。**
`DataValidationBuilder` に該当メソッドが無く、API v4 の `DataValidationRule` も
`condition` / `inputMessage` / `strict` / `showCustomUi` の4フィールドしか無い
（2026-07 時点で確認）。ここだけ手作業になる。

1. 「タグ確認」シートの **G2** を選択
2. **データ > データの入力規則** → 出てきたルールをクリック
3. **(a) 詳細オプション → 表示スタイル を「チップ」にする**
   Apps Script から作ると「矢印」になることがあり、
   「複数の選択肢を許可」はチップ形式でしか出てこない。
4. **(b)「複数の選択肢を許可」にチェック**
5. **(c)** 各タグ名の左の丸 → **Customize** に「タグ一覧」シートB列の色を貼る（11回）

現行タグ列(G)と修正後タグ列(H)は**隣接させて同一の検証ルールを共有**させてあるので、
この1回の設定が両方に効く。`setup` を再実行してもルールが同じなら
`addValidation_` は何もしないので、設定は保持される。

(a) を入れるまでは複数タグの入ったセルに無効フラグが付く。チェックを入れれば消える
（そのため `addValidation_` は `setAllowInvalid(true)` にしてある）。

### 4. 共有

Myu さん・椎名さん・おりえさんを編集者として招待し、「ルール」シートを最初に見てもらう。

### 5. 確認完了後（フェーズ2への受け渡し）

1. 「タグ確認」シートを **ファイル > ダウンロード > カンマ区切り形式** で保存
2. `out/reviewed.csv` として配置
3. 実行

```bash
python3 tag_review/ingest_reviewed.py
```

語彙外のタグ・タグ0個・4個超・行の欠落や重複を検証し、
1件でも引っかかれば `out/reviewed_tags.json` を出力せず終了する。
不正なタグ集合をタグ割合の計算に流さないため。
原則上限3を超える4タグのケースは、止めずに「例外」として一覧報告する。

## シートの構成

**「タグ確認」** — 1ケース1行、88行。

| 列 | 内容 | 編集 |
|---|---|---|
| A `No` | 椎名さんの通し番号 | 保護 |
| B `case_id` | CALL4のID | 保護 |
| C `状況` | アーカイブ / 進行中 | 保護 |
| D `メモ` | 椎名さんのメモ＋自動注記 | 保護 |
| E `ケース名` | CALL4ページへのリンク付き | 保護 |
| F `概要` | 掲載説明文（200字以内） | 保護 |
| G `現行タグ` | マルチセレクト（色付きチップ） | 保護 |
| H `修正後タグ` | マルチセレクト（色付きチップ）／オレンジ枠 | **記入** |
| I `変更あり?` | 自動判定 | 数式 |
| J `コメント・理由` | 自由記述 | **記入** |
| K `確認者` | 記入者名 | **記入** |
| L `CALL4最終判断` | おりえさん用 | **記入** |

H列は 0個のとき赤。4個以上のときは **A列（No）** がオレンジになる（禁止ではなく目印）。
マルチセレクトなので同じタグの重複入力は原理的に起きない。

**「タグ一覧」** — 11タグのチップ色見本（B列）と、現行件数・修正後件数・増減が
リアルタイムで見える。おりえさんの「全体のバランスを担保したい」という要件に対応する面。
修正後件数が3件未満のタグは赤くなる。

**「ルール」** — 依頼内容と操作方法。

## 設計上の判断

- **「アーカイブ」はタグ列に入れない。** 上限3のカウント対象外なので、C列「状況」で表す。
  実データでもアーカイブを除くと4タグは1件（リンさんのケース）だけで、
  おりえさんの説明（上限3、リンさんのみ例外的に4）と完全に一致する。
- **リンさんのケースは現行の4タグを初期値として入れてある。** 3つに減らすか4つ維持かは
  判断事項なので、どちらも選べる形にした。こちらで3つ選んで初期値にすると判断を誘導するし、
  空欄にすると「維持」を選びにくくなる。
- **タグはマルチセレクトの1列にまとめた。** 1セル1タグの4列構成から変更。
  横幅が縮み、重複入力が原理的に起きなくなり、上限個数の変更にも列構成が影響されない。
  区切りは Sheets が使う **`", "`（カンマ+半角スペース）** でなければチップとして
  認識されないので、`make_tag_review.py` の `SEP` はこれで固定。
- **現行タグ列と修正後タグ列を隣接させ、同一の検証ルールを共有させる。**
  手作業（表示スタイル＋複数選択の許可＋チップ色11個）が1回で両方に効くようにするため。
- **タグ列(G/H)にはセルの塗りを一切かけない。** セルを塗るとチップの色が埋もれて
  「セル全体が塗られている」ように見えてしまう。色はチップだけが持つ。
  記入欄であることは塗りではなくオレンジの枠線で示し、
  上限超過の目印もタグ列ではなくA列（No）に出している。
- **件数集計と変更判定は部分一致で行う。** 1セルに複数タグが入るので、
  `COUNTIF` のワイルドカードと `SEARCH` を使う。どのタグも他タグの部分文字列で
  ないことを `make_tag_review.py` が起動時に検証している（ここが崩れると誤カウントする）。
- **変更判定は入力順に依存しない。** 現行側・修正後側の両方を「タグ一覧」の並び順で
  組み直してから文字列比較する。選んだ順番が違うだけでは「変更」にならない。
- **ケース名のリンクはリッチテキストで埋め込む。** `HYPERLINK` 数式にすると
  CSVに書き出し直したときに数式文字列になり、`ingest_reviewed.py` の再取り込みが壊れる。
- **読み取り専用列は警告付き保護（完全ロックにしない）。** 気づいた誤りを
  その場で直せる余地を残す。編集時には警告が出る。
- **CSVはBOM無しUTF-8で出力する。** BOM付きだとA1が `"\ufeffNo"` になり、
  `setup.gs` の見出し検出が落ちる。

## タグの色について

dataviz スキル同梱の ΔE / CVD 実装（Machado 2009、OKLab ΔE×100）で探索・実測した。
スプレッドシートでは任意の2タグが縦に隣接しうるので all-pairs で評価している。

| 色数 | 通常視 最小ΔE | protan | deutan |
|---|---|---|---|
| 4 | 14.0 | 8.2 | 6.2 |
| 6 | 10.0 | 3.9 | 3.2 |
| 11（色相等間隔） | 5.5 | 2.3 | 0.9 |
| **11（最適化後・採用）** | **10.9** | 1.1 | 0.6 |

- **11色は二色覚下では識別できない**（最小ΔE 0.6）。これは原理的な限界で、
  二色覚下では色相軸が1次元に潰れるため、11方向を離すには明度を振るしかなく、
  それは「順位がある」という誤ったメッセージになる。
  セルには必ずタグ名が入るので、識別は文字が担保する前提の配色として採用した。
- 色相等間隔に置くと通常視でも最小ΔE 5.5 しか出ないので、明度・彩度も自由変数にした
  farthest-point 選択＋局所改善で 10.9 まで押し上げてある。
- 彩度は 0.12（OKLCH C）で上限を切った。上限まで使うと最小ΔE 16.5 まで伸びるが、
  蛍光色になって88行に敷くと目に痛い。
- 付与件数の多いタグに淡い色、稀なタグに濃い色を割り当てている
  （`公正な手続` は88件中38件なので最も淡い `#daecfd`）。稀なタグが目に留まる副作用もある。
- 文字色に色を付ける案は逆に悪化した。本文の可読性 4.5:1 を満たすには明度を落とす必要があり、
  色域内で彩度が取れず11色・8色は解が存在しない。

## フェーズ2への申し送り

`沖縄` 2件・`個人情報・プライバシー` 1件は、[plan05.md](../plan05.md) の
判別プロトタイプ法では陽性件数が足りずタグ割合の計算が成立しない（陽性2件未満はLOO不能）。
フェーズ1でここに貼り忘れが見つかると次工程の安定性が直接改善するので、
「タグ一覧」シートで件数を可視化して自然に目に入るようにしてある。

逆に `公正な手続` は88件中38件（43%）で識別力がほぼない。ここが動くと
全体の割合が最も大きく変わるため、フェーズ2の再計算はフェーズ1の確定後に行う必要がある。
