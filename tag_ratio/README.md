# タグ割合の再計算と確認シート（フェーズ2）

フェーズ1（`tag_review/`）で確定したタグを使って、**ケース内のタグ割合**を
計算し直し、その割合をもう一度スプレッドシートで人に確認してもらう一式。
確定した割合はカードの帯とタグ↔ケースの2部グラフ（`card_editor/`）に流れる。
作成: 2026-08-20。

```
生データ(cache/)  ─┐
確定タグ(フェーズ1) ┴→ s0_cases.py → cases_reviewed.json
                                          ↓
                     bge-m3埋め込み → s1_ratios.py → soft_tags.json（計算値）
                                          ↓
                              s2_make_ratio_sheet.py → ratio_review.csv
                                          ↓  ＋ setup_ratio.gs
                                   【Googleスプレッドシートで人が確認・修正】
                                          ↓  reviewed_ratios.csv
                              s3_ingest_ratios.py → soft_tags_final.json
                                          ↓
                    card_editor/s2_make_cards.py → s3_build_editor.py → GitHub Pages
```

## ファイル

| ファイル | 役割 |
|---|---|
| `s0_cases.py` | 生データ＋確定タグから「ケース情報」を1本に組み直す |
| `s1_ratios.py` | 割合を再計算（plan05と同じ方法・入力だけ差し替え） |
| `s2_make_ratio_sheet.py` | 確認用スプレッドシートのインポートCSVを生成（順番→割合の導出規則もここ） |
| `setup_ratio.gs` | シート側の書式・数式・条件付き書式・メニューを一括設定 |
| `s3_ingest_ratios.py` | 確認済みシートを読み戻して検証し、確定版を作る |
| `out/cases_reviewed.json` | 88件のケース情報（確定タグ入り）。後段の唯一の入力 |
| `out/soft_tags.json` | 再計算した割合（`plan05/results/soft_tags.json` と同じ構造） |
| `out/ratio_review.csv` | インポートするCSV（生成物） |
| `out/ratio_baseline.json` | 計算値の控え（読み戻し時の差分判定に使う） |
| `out/reviewed_ratios.csv` | 確認済みシートのダウンロード（手で配置。**Git管理外**） |
| `out/soft_tags_final.json` | 人の判断を反映した確定版（**Git管理外**） |
| `phase1_notes.py` | フェーズ1の「齟齬確認」メモを機械可読にする（単体で実行すると解釈結果を一覧表示） |

`out/` のうち `soft_tags.json` 以外は追跡しない。確認者名とフェーズ1のメモが
入るため（このリポジトリは GitHub Pages のために公開してある）。
`soft_tags.json` は数値だけなので追跡する。

## フェーズ1の申し送りを引き継ぐ

フェーズ1のシートには、当初の設計に無かった列が確認者の手で追加されていた。

| 列 | 中身 | 扱い |
|---|---|---|
| `マッピング(スクショ)との齟齬確認` | 旧マップのスクショを見ながら書いた**タグの大小関係**（例 `外国>手続`）50件 | `phase1_notes.py` で解釈し、シートのH列と照合列に載せる |
| `ポスターカラー変更` | TRUE/FALSE 88件 | FALSE の12件を**未決着**と読む |

「割合はこうあるべき」という判断がすでに書かれているので、フェーズ2の
入力として引き継ぐ。ただし自由記述なので**確実に読める形だけ**を制約にする。

- `A>B` / `A<B` / `A>B>C` / `A>>`（Aが最大）→ 制約として読む（41件）
- `?`「わかんない」「気がする」「一旦」等を含む → **暫定**として読む
- 記号が混在（`環境>><手続`）・向きが無い（`他のタグの影響強い`）→ **解釈しない**（9件）。
  原文だけをシートに載せて人に返す

再計算した割合との照合結果は **一致31 / ほぼ同率2 / 不一致8**。
差が2%未満のものを「一致」と表示すると実質同率なのに確認済みに見えるので、
`≒` として分けている。

`ポスターカラー変更` の解釈は推測（FALSE の12件が迷いの書かれた行と完全に
一致することが根拠）。違っていれば `phase1_notes.py` の `DECIDED_COL` の扱いを直す。

## 手順

### 0. 前提：フェーズ1の確定タグ

```bash
# スプレッドシート「タグ確認」を CSV でダウンロードして
#   tag_review/out/reviewed.csv として配置してから
python3 tag_review/ingest_reviewed.py      # → tag_review/out/reviewed_tags.json
```

### 1. ケース情報と割合の再計算

```bash
.venv/bin/python tag_ratio/s0_cases.py     # → out/cases_reviewed.json
.venv/bin/python tag_ratio/s1_ratios.py    # → out/soft_tags.json
.venv/bin/python tag_ratio/s2_make_ratio_sheet.py   # → out/ratio_review.csv
```

`s1_ratios.py` は `plan02/features/emb.npz`（bge-m3の埋め込み）が必要。
派生バイナリなのでGitには入っていない。無い場合は
`plan02/s1_features.py` で作り直す（bge-m3のダウンロード約2.3GB、
95件のエンコードにCPUで約9分）。テキスト構成は plan02 Stage 0 と同一なので、
作り直しても以前と同じ値が再現する（実測: 割合の差 0.000、AUC完全一致）。

### 2. スプレッドシートを作る

1. 新規スプレッドシートを作成
2. **ファイル > インポート** で `out/ratio_review.csv` を取り込む
   （インポート場所「現在のシートを置換する」、区切り文字「カンマ」）
3. **拡張機能 > Apps Script** を開き、`setup_ratio.gs` を全部貼り付けて保存
4. 関数 `setup` を実行（初回のみ権限承認）
5. シートを再読み込みするとメニュー「割合ツール」が出る

フェーズ1と違い**手作業で仕上げる箇所は無い**。マルチセレクトのチップを
使わないので、Apps Script だけで完結する。`setup` は冪等。

### 3. 共有

Myu さん・椎名さん・おりえさんを編集者として招待し、「ルール」シートを最初に見てもらう。

### 4. 確認完了後

1. 「タグ割合」シートを **ファイル > ダウンロード > カンマ区切り形式** で保存
2. `out/reviewed_ratios.csv` として配置
3. 実行

```bash
.venv/bin/python tag_ratio/s3_ingest_ratios.py
```

**正は「順番」列**で、割合はここで作り直す（シートの割合列は数式の結果＝表示用）。
シートの数式が古いままでも成果物の数字は狂わない。導出は
`s2_make_ratio_sheet.apply_order` を共用し、シートの表示と食い違えば警告する
（数式のバグに気づくため）。

タグ集合の食い違い・行の欠落や重複・順番の未選択・計算値の書き換えを検証し、
1件でも引っかかれば `soft_tags_final.json` を出力せず終了する。

### 5. カードと2部グラフに反映

```bash
.venv/bin/python card_editor/s2_make_cards.py      # カード画像を作り直す
.venv/bin/python card_editor/s3_build_editor.py    # 配置エディタを作り直す
./card_editor/deploy_pages.sh                      # GitHub Pages を更新
```

`card_editor/s2_make_cards.py` は割合を**新しい順に**探す
（`soft_tags_final.json` → `tag_ratio/out/soft_tags.json` → `plan05/results/soft_tags.json`）。
どれを使ったかを標準出力に出すので、暫定値のまま版下を作ってしまうことはない。
配置（`layout_manual.json`）はケースIDで持っているので、カードを作り直しても
これまでの配置作業は無駄にならない。

## シートの構成

**「タグ割合」** — 1ケース1行、88行。

| 列 | 内容 | 編集 |
|---|---|---|
| A `No` | 椎名さんの通し番号 | 保護 |
| B `case_id` | CALL4のID | 保護 |
| C `状況` | アーカイブ / 進行中 | 保護 |
| D `ケース名` | CALL4ページへのリンク付き | 保護 |
| E `概要` | 掲載説明文 | 保護 |
| F `タグ数` | 1〜3（スロットは4まで） | 保護 |
| G `タグ（検索用）` | タグを連結した文字列（フィルタ用） | 保護 |
| H `フェーズ1の指摘` | 齟齬確認メモの原文（未決着なら【未決着】付き） | 保護 |
| **I `順番`** | **プルダウン。ここだけが記入欄** | **記入** |
| J–U | `タグk` / `計算k`（非表示） / `割合k` × 4スロット | すべて自動 |
| V `合計` | 数式。常に100 | 数式 |
| W `指摘と一致?` | 数式。◯ / ≒ / × / 空 | 数式 |
| X `色の変化` | 数式。主タグ（ポスターの色）が旧マップから変わる行だけ「旧 → 新」 | 数式 |
| Y `変更あり?` | 数式。計算と違う順番を選ぶと「変更」 | 数式 |
| Z–AB | コメント・理由 / 確認者 / CALL4最終判断 | **記入** |
| AC `指摘の読み取り` | 照合の数式を組む作業列（非表示） | 保護 |
| AD `旧マップの主タグ` | 色比較の基準（非表示） | 保護 |
| AE `既定の順番` | 「変更あり?」と押し広げの判定基準（非表示） | 保護 |
| AF–AI `調整k` | 押し広げ後の割合。順位1..4に渡す値（非表示） | 保護 |

押し広げ後の値は `s2_make_ratio_sheet.py` が計算して `調整k` 列に書き込み、
シートの数式はそれを `CHOOSE(順位, 調整1..調整4)` で参照するだけにしてある。
同じアルゴリズムをGASとPythonの2か所に持たないため。

`順番` のプルダウンは行ごとに中身が違う（そのケースのタグの並べ替え）。
2タグなら2通り＋「どれも同じくらい」、3タグなら6通り＋同。
1タグの35行にはプルダウンを置いていない。

**`計算k` は非表示にしてある。** 人が見るべき数字は `割合k` だけで、
2種類の数字が並んでいるとどちらを判断すればよいのか分からなくなる。
消さずに隠すのは、`割合k` の数式がこの値を元にしているため
（読み戻しも参照する。非表示の列もCSVには書き出される）。

## 版の食い違いを弾く

`setup` は最初に `assertLayout_` で見出しの並びを確認し、想定と違えば
どの列が違うのかを名指しして止める。CSVとスクリプトの版が食い違うと、
列番号がずれたまま数式が入って**分かりにくい壊れ方**をするため。

実際に一度これを踏んでいる（順番方式より前のスクリプトを新しいCSVに当てた）。
旧版の「変更あり?」は `N(修正)=N(計算)` を旧列番号で比較していたので、
新CSVでは列10が`タグ1`（文字列）・列11が`計算1`（数値）となり
`0≠44` で**全88行が「変更」**になっていた。

同じ理由で「変更あり?」の数式も隠し列を参照しない形に変えた。
計算どおりの順番＝タグ列の並び（スロットは計算値の降順）なので、
`TEXTJOIN` でタグ列を連結して比べている。列がずれても静かに誤判定しない。

`setup` 完了時のダイアログと「ルール」シートの末尾に版
（`VERSION`）を出しているので、症状が出たときにどちらの版かを確認できる。

`指摘と一致?` は静的な値ではなく**数式**にしてある。順番を選び直した瞬間に
判定が変わるので、狙いどおりになったかがその場で分かる。
タグ列と割合列は2列おきなので、`SUMIF(タグの範囲, タグ名, 2列右の範囲)`
でそのタグの値を取っている（タグは1行に1回しか出てこないので合計＝その値）。
割合そのものも数式で、順位は「順番」の文字列中での出現位置を他のタグと
比べて数えている。渡す値は4通り（1タグ→計算値／「どれも同じくらい」→均等割り／
既定のまま→計算値／既定と違う順番→`調整k`）。
判定の閾値（2%）は `phase1_notes.py` の `TIE_PT` と揃えてある。
`!` が出たら数式が評価できていない（想定外なので知らせてほしい）。

`色の変化` は、確認者がフェーズ1で「ポスターカラー変更」列を作って
追っていた関心事をそのまま列にしたもの。基準は確認者が見ていた
スクリーンショットのもとになった割合（`plan05/results/soft_tags.json`、
生タグ・95件）で、**4件**で色が変わる。うち3件はフェーズ1の指摘と
逆向きの変化なので（`沖縄>情報公開` `外国>手続` `働き方>ジェンダー`）、
V列が × になっている行と重なる。

**「タグ別サマリ」** — タグごとの付与件数・重み合計・平均割合・増減。
重み合計＝各ケースの割合の合計（そのタグが全体の何ケース分に相当するか）で、
紙のマップではタグから伸びる線の太さの合計になる。付与件数が同じでも
割合を下げれば重みは減るので、「全体のバランス」はここで見る。

**「ルール」** — 依頼内容と操作方法。

**メニュー「順番ツール」** — 選択行をフェーズ1のメモどおりにする /
選択行を計算どおりの順番に戻す / 全行を点検する。

## 設計上の判断

- **人が入れるのは「順番」だけ。数値は打たせない。** 実質53件に対して数字を
  1つずつ決めてもらうのは現実的でなく、「40か45か」に判断の根拠も無い。
  決められるのは**どちらが主役か**なので、そこだけを聞く。実際フェーズ1でも、
  確認者は自由記述欄に `外国>手続` という形で書いていた。
- **割合は「順番に計算値の大きさを割り当て直す」形で決める。**
  1位に計算値の最大、2位に2番目…と当てはめる。つまり**差の大きさは本文から
  出た値を活かし、向きだけ人が決める**。既定のままなら数字は1つも動かないので、
  「触っていない」ことがそのまま担保される。固定の比（60:40など）を当てる方式にすると、
  46件ある2タグのケースが全部同じ比になり、ケースごとの濃淡が消えてマップが平坦になる。
- **既定と違う順番を選んだときは、隣り合う差を最低10ptまで押し広げる。**
  計算が 50:50 や 34:33:33 のケースで順番を変えても、大きさを入れ替えるだけでは
  数字が動かず、**人が決めたことが紙に出ない**。押し広げは足りない差だけを開き、
  既に10pt以上ある差はそのまま残す（計算の濃淡を壊さない）。
  53件のうち効くのは10件で、残り43件は計算値のまま。
  2タグなら 55:45、3タグの同率なら 43:33:24 になる。
- **押し広げるかどうかの基準は「既定の選択肢と違うか」。** スロット順と比べては
  いけない。ほぼ同率の行は既定が「どれも同じくらい」なので、スロット順を選ぶこと
  自体が人の判断であり、スロット順と比べると押し広げが効かない
  （実装当初これを踏んだ）。
- **計算がほぼ同率（差が2pt未満）の行は、既定を「どれも同じくらい」にする。**
  機械の側に「どれが主役か」の情報が無いのに計算の並び順を既定にすると、
  根拠のない順位を主張することになる。該当2件（I0000085・I0000146）。
- **「どれも同じくらい」を選べるようにした。** 順番を必ず1つ決めさせると、
  実質同率のケースに嘘の順位が付く。
- **付与タグの割合には10%の下限を設ける（`MIN_SHARE_PT`）。**
  1%はカードの帯で0.84mm——罫線より細く、「1%」という数字自体が入らない。
  **タグはケース主催者の意思で付いている**ので、本文から読み取れなくても
  読める太さで描かないとそのケースの趣旨を落としてしまう。機械の推定より
  人の付与を尊重する判断。該当3件（`I0000104` 98:1:1、`I0000141` 69:30:1、
  `I0000052` 91:9）。
  引く先は10%を超えている側で、**超過分に比例**して削る
  （超過値がどれも同じ倍率で縮む形なので順位と相対関係は崩れない）。
  「最大の1つからまとめて引く」案は2位を据え置くため1位と2位の差が縮みすぎ、
  「全員に10%配って残りを再配分」案は差が十分あるケースの濃淡まで壊すので採らなかった。
  底上げした分は紙の上で実際より重く見えるので、レポートに明記してある。
- **底上げは押し広げより優先する。** 両方が効く場面では最低差10ptを満たせないことが
  あるが、読めない帯を作らない方を優先する。
- **差の大きさ自体は変えられない。** 変えたい場合はコメントに書いてもらう。
  ここで数値も触れるようにすると「順番だけ決めればよい」という単純さが失われる。
- **1ケース1行（横に4スロット）にした。** 「このケースの中で何が主役か」の
  判断は横一列で見えないとできない。タグを縦に展開する long 形式は
  1ケースを読むのに複数行を追う必要があり、判断に向かない。
- **割合は合計100の整数％で持つ。** カードの帯に出る数字も整数％なので、
  人が見る値と成果物に出る値が一致する。小数第3位まで見せても判断材料にならない。
- **付与タグの下限は1％。** 0％はカードの帯から消えてしまい、
  「タグが付いているのに描かれない」という矛盾が起きる。
  最大剰余法で丸めたあと、0になったタグを1％に持ち上げて最大スロットから引く。
- **タグが1つのケース（88件中35件）も行として残す。** 100％固定で判断の余地は
  無いが、行を落とすと「なぜ自分のケースが無いのか」という疑問が生まれる。
  淡いグレーにして「触らなくてよい」ことを示し、F列でフィルタできるようにした。
  順番を選ぶ対象は**53件**（2タグ46・3タグ7）。
- **スロットは4つ用意してある。** フェーズ1で4タグのケース（リンさんの事件）が
  3タグに減ったので現状は3で足りるが、タグが増えたときに列構成を
  作り直さずに済むよう4のままにしてある。
- **タグ自体はこのシートで変えられない。** 割合とタグを同時に動かすと、
  タグが変われば割合の計算前提（プロトタイプ）も変わるため、
  どちらの判断を反映した数字なのかが分からなくなる。タグを直したい場合は
  コメントに書いてもらい、フェーズ1に戻す。`s3_ingest_ratios.py` は
  タグ集合が確定と違えばエラーで止める。
- **合計は構造的に100になる。** 割合は計算値（合計100）の並べ替えか均等割りしか
  取らないので、合計がずれる状態が存在しない。人に足し算をさせない。
- **「順番ツール > 選択行をフェーズ1のメモどおりにする」を付けた。**
  指摘と食い違う8件を1クリックで直せる。動かすのは**メモに出てくるタグだけ**で、
  メモが言っていないタグの順位は変えない（例: いま「刑事 ＞ 外国 ＞ 手続」で
  メモが `外国>手続` なら、2位・3位の並びは既に条件を満たしているので何も変えない）。
  メモが言っていないことまで決めてしまわないための最小限の入れ替え。
- **初期値は計算どおりの順番。** 空欄から始めると「機械の推定を無視して自分で決める」
  作業になり、53件は現実的に終わらない。「違うと思ったところだけ直す」形にする。
- **色はフェーズ1・カード・2部グラフと同じ11色。** タグ名セルだけを塗り、
  数字のセルは塗らない（数字の可読性を落とさないため）。
- **不一致（×）でも計算値をそのまま初期値にしている。** 指摘に合うように
  こちらで数字を作ると、機械の値でも人の判断でもない第三の数字になる。
  食い違いを可視化して人に決めてもらう。

## 母集団を88件にしたこと（plan05 からの変更）

plan05 は95件で計算していたが、フェーズ2は**88件**（音信不通7件を除く）で計算する。
除外した7件は目視確認を受けていないので、確定タグと未確認タグが混ざった
プロトタイプになる。最終成果物の対象も88件なので母集団を揃えた。

副作用として稀なタグの陽性件数が減る。`沖縄` は2件・`個人情報・プライバシー` は
1件しかなく、後者はプロトタイプが作れないため **AUCを計算できない**（低信頼）。
`沖縄` の AUC は 0.48 で、これは「テキストからは判別できていない」ということ。
これらのタグが付いたケースの割合は、機械の値より人の判断を優先してほしい。
シートの「ルール」にも計算値の性質として明記してある。

## 将来の改善案（未着手）

**割合を出す段で、コサイン類似度の差を圧縮する。**
いまは softmax の温度 τ をデータのばらつき（付与タグの disc の標準偏差）から
自動で決めているため、本文の寄りが強いケースでは 98:1:1 のような極端な配分になり、
最低割合の底上げで後から手当てしている。τ を意図的に緩めるか、
別の関数を挟んで差を圧縮すれば、底上げに頼らずに済むはず。
「極端なコサイン類似度の差異があっても割合そのものに極端な差異を生まない」形が理想。
今回は触っていない（確定データを作り直すことになるため）。
